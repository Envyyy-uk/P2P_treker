# Фаза 4.1 — Модель капіталу: що зроблено

Моніторинг капіталу поверх того самого `BalanceManager` (Фаза 4), що вже
гарантує "капітал заздалегідь розподілений, без withdraw під кожну угоду".
`CapitalMonitor` (`app/capital/monitor.py`) додає: снепшот балансу по
біржах, target allocation, сигнал ребалансування, real-time перевірку
доступності напрямку, ручний переказ.

| Компонент плану | Реалізація |
|-----------------|------------|
| Капітал заздалегідь розподілений; без withdraw під угоду | Успадковано з `BalanceManager` (Фаза 4) — Paper Trading й так ніколи не "виводить" кошти, тільки резервує/списує з наявного балансу |
| Купівля/продаж за рахунок наявних балансів | Те саме — `PaperTradingEngine` (Фаза 4) уже працює виключно через `BalanceManager.reserve/settle` |
| Ребалансування — окремий процес | `CapitalMonitor` тільки рахує і сигналізує; `record_manual_transfer` лише фіксує в обліку переказ, який оператор уже зробив на реальних біржах — жодного автоматичного переказу коштів |
| Моніторинг балансу (base/quote, locked/available) | `CapitalMonitor.snapshot()` → `ExchangeCapitalStatus` (quote-актив + dict base-активів, кожен з total/available/locked) |
| Напрямок тимчасово вимикається при нестачі балансу | `CapitalMonitor.check_direction()` — stateless real-time перевірка обох ніг (quote на buy-біржі, base на sell-біржі) поверх `BalanceManager`, а не окремий персистентний прапор (баланс і так єдине джерело правди) |
| Target allocation на біржу | `CapitalConfig.target_allocation: dict[Exchange, Decimal]` (%, має сумувати до 100) |
| Сигнал про ребалансування | `CapitalMonitor.rebalance_signals()` — жадібне спарювання найбільшого надлишку з найбільшим дефіцитом понад `rebalance_threshold_pct` |
| Ребалансування спочатку ручне | `record_manual_transfer()` — тільки бухгалтерська фіксація, не виконання |
| Автоматичне ребалансування — тільки після стабільного execution layer | Свідомо не реалізовано в цій фазі (нижче) |

## API

```text
GET  /api/capital/status              снепшот балансу по всіх увімкнених біржах
GET  /api/capital/rebalance-signals   список сигналів (порожньо, якщо target не задана
                                       або відхилення в межах rebalance_threshold_pct)
POST /api/capital/check-direction     {"symbol", "buy_exchange", "sell_exchange",
                                        "quantity", "buy_price"} -> available: bool + reason
POST /api/capital/transfer            {"asset", "from_exchange", "to_exchange", "amount"}
                                       фіксує РУЧНИЙ переказ (не виконує його)
```

## Розподіл капіталу рахується тільки за quote-активом (USDT)

`actual_pct`/`target_pct`/`deviation_pct` та `rebalance_signals` оперують
виключно балансом `quote_asset` (дефолт USDT) на кожній біржі. Конвертація
base-активів (BTC, ETH, ...) у спільну грошову одиницю вимагала б живих
цін конвертації і вносила б залежність від quote cache в модуль, що мав
би лишатися простим і детермінованим — окрема, ширша задача поза межами
цієї фази. `base_asset_statuses` у `/api/capital/status` показує base-баланси
окремо (total/available/locked) саме для моніторингу (план, п.5), просто
не бере участі в розрахунку відсотків розподілу.

## Свідомо не зроблено в цьому проході

- **Автоматичне ребалансування** (план, п.10: розглядати лише після
  стабільної роботи execution layer, якого ще не існує — Фаза 5). Тому
  `record_manual_transfer` — єдиний спосіб змінити розподіл капіталу між
  біржами, і він лише синхронізує внутрішній облік із тим, що оператор
  вже зробив вручну на реальних біржах.
- **Персистентний "disabled" стан напрямку**. Свідомий вибір: замість
  окремого stateful прапора "цей напрямок вимкнено" (який довелося б
  синхронізувати з балансом і десь зберігати між запитами), `check_direction`
  рахується наживо з `BalanceManager` при кожному виклику — простіше,
  завжди актуально, немає ризику розсинхронізації.
- **Конвертація base-активів у спільну валюту для розподілу** (див. вище).

## Перевірено в цьому середовищі

- Юніт-тести (`test_capital_monitor.py`, 15 тестів): `actual_pct` коректно
  рахується від сумарного quote-капіталу; `target_pct`/`deviation_pct`
  `None`, якщо target не налаштована; `None` для `actual_pct`, якщо
  сумарний капітал 0; base-активи (включно з locked) присутні в снепшоті;
  сигнал ребалансування відсутній у межах порогу і без налаштованої
  target; сигнал коректно генерується і матчиться (перевірено суму
  переказу проти вручну порахованого очікуваного значення); `check_direction`
  — доступно, недоступно через quote на buy-біржі, недоступно через base
  на sell-біржі; `record_manual_transfer` — успішний переказ і атомарна
  відмова (без часткової мутації) при нестачі коштів на джерелі.
- `BalanceManager.debit` (`test_balance.py`, +3 тести): списання при
  достатньому балансі, відмова без мутації при нестачі, врахування
  вже заблокованих (`locked`) коштів.
- Інтеграційні тести (`test_capital_routes.py`, реальний `app`, БД
  вимкнена): `/status` повертає всі три увімкнені біржі з коректними
  quote-балансами; `/rebalance-signals` порожній без налаштованої target;
  `/check-direction` доступно за замовчуванням і недоступно після
  вичерпання балансу конкретної біржі (спільний стан із Paper Trading —
  той самий `BalanceManager`); `/transfer` реально рухає кошти між
  біржами (перевірено через наступний `GET /api/paper-trading/balances`),
  400 на однакову біржу/невалідну суму/нестачу коштів.
- Живий запуск повного застосунку (`uv run uvicorn` + `curl`, реальний
  Postgres 16 на фоні): дефолтний рівний розподіл 33.33%/33.33%/33.33%
  без target; `check-direction` коректно перемкнувся на `available:false`
  після виснаження балансу binance і назад на `true` після
  `POST /transfer`; окремий прогін з `CAPITAL__TARGET_ALLOCATION=
  {"binance":"70","bybit":"20","okx":"10"}` підтвердив, що
  `/rebalance-signals` при фактичному рівному розподілі коректно
  пропонує перекинути кошти з okx і bybit на binance (суми і знаки
  відхилень співпали з ручним розрахунком); graceful shutdown відпрацював
  штатно в обох прогонах.
- Повний прогін: 293 тести по backend (+25 від цієї фази), `ruff check` —
  чисто, `black --check` — чисто, `mypy app` (strict) — `Success: no
  issues found in 74 source files`.
