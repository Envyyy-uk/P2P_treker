# Фаза 3.1 — Historical Backtesting Engine: що зроблено

Прогонює історичні `quotes_1s` через **ту саму** логіку `SpreadEngine` +
`SpreadEventTracker`, що працює live (Фази 1/2) — жодного дублювання формул
чи детектора подій окремим кодом. Read-only: не пише в БД, не впливає на
live-моніторинг чи вже записані `spread_events`.

| Компонент плану | Реалізація |
|-----------------|------------|
| Взяти історичні quotes_1s за період | `BacktestEngine._load_ticks` — SELECT з `quotes_1s` (parent partitioned table, Postgres сам робить partition pruning), ordered by timestamp |
| Прогнати через ту саму логіку Spread Engine | `BacktestEngine.run`: реальний `SpreadEngine` (той самий клас, що й live) + реальний `SpreadEventTracker` (той самий клас, що й Фаза 2), відтворені тік-за-тіком у власному `QuoteCache` |
| Змінювати параметри заднім числом | `BacktestParams`: `spread_threshold`, `min_duration_ms`, `fee_overrides` (per-exchange), `min_executable_quantity`/`min_executable_notional` — усе застосовується тільки до цього прогону, ніколи до збережених `spread_events` |
| Симульований PnL з урахуванням комісій | `sum(estimated_profit)` по подіях, що пройшли `min_duration_ms`; `estimated_profit` вже комісійно-скоригований через `formulas.expected_net_profit` |
| Позначення як оптимістична оцінка | `BacktestResult.disclaimer` — присутній у кожній відповіді API |
| Не оптимізувати під історичні дані (overfitting) | Задокументовано як методологічна вимога (нижче); код цього не може "виявити" автоматично — відповідальність дослідника |

## API

```text
POST /api/backtest/run
{
  "symbols": ["BTC-USDT"],
  "from": 1784246400000,
  "to": 1784246430000,
  "spread_threshold": "0.002",       // опціонально, інакше з конфігу
  "min_duration_ms": 500,             // опціонально, дефолт 0
  "min_executable_notional": "50",    // опціонально
  "fee_overrides": {"binance": "0.0002"}  // опціонально, per-exchange
}
```

## Як працює replay

1. Завантажити всі рядки `quotes_1s` для заданих символів/періоду
   (обмежено `BACKTEST__MAX_TICKS_PER_RUN`, дефолт 500 000 — захист від
   випадкового запиту на роки історії в один прогін).
2. Згрупувати рядки за точним `timestamp` (усі біржі семплюються в один і
   той самий момент у `HistoryRecorder`, Фаза 2 — групування природно
   вирівнює тіки різних бірж).
3. Для кожного тіка: покласти нові котирування в `QuoteCache`, викликати
   `SpreadEngine.compute_all(now_ms=tick_ts)` (та сама freshness-логіка,
   що й live — застарілі/невирівняні дані так само позначаються invalid).
4. Згодовати результат у `SpreadEventTracker.process(...)` — та сама
   логіка перетину порогу, що й live/Фаза 2.
5. Після проходу — `tracker.flush_open(...)`, щоб не втратити подію, яка
   ще не закрилась на кінець періоду (як graceful shutdown у Фазі 2).
6. Відфільтрувати події коротші за `min_duration_ms` (read-side, не
   впливає на семантику детектора) і порахувати сумарний/середній PnL.

## Важливі обмеження (свідомо, як і застерігає план)

- **Комісії при заміні через `fee_overrides` застосовуються до ВСЬОГО
  періоду** — це не історична реконструкція комісій "як було насправді
  того дня", а сценарій "що якби комісія була іншою" (план, п.3:
  "щоб оцінити чутливість до зміни VIP-рівня").
- **Без VWAP/slippage/затримки виконання/конкуренції з іншими ботами**
  (Фаза 4). `estimated_profit` — обсяг і ціна на момент максимального
  спреду, не symulated fill.
- **Overfitting:** якщо параметри (поріг, min_duration, комісії)
  підібрані так, щоб ідеально пасувати конкретному історичному періоду,
  результат нічого не каже про майбутнє. Перевіряйте той самий набір
  параметрів на іншому, не використаному в підборі періоді (out-of-sample)
  перш ніж довіряти висновку.

## Перевірено в цьому середовищі

- 14 нових тестів (9 unit для валідації `BacktestParams` — інвертований
  діапазон, невідомий символ, non-spot market, frozen dataclass; 5
  route-тестів із fake engine — серіалізація, передача експериментальних
  параметрів, 400/503); 186 тестів у сумі по backend; ruff, black,
  mypy strict — чисто.
- Реальний Postgres 16: засіяно 30 секунд котирувань двох бірж з чітким
  6-секундним сплеском спреду (~1.75% net) на тіках 10–15. Перевірено:
  - дефолтні параметри знаходять рівно 1 подію тривалістю точно 6000мс,
    напрямок binance→bybit, додатний PnL;
  - підвищення порогу до 2% (вище фактичного ~1.93% net) прибирає подію;
  - `min_duration_ms=7000` (довше за фактичні 6000мс) відфільтровує подію;
  - комісії 5%+5% "з'їдають" спред — подія зникає;
  - штучно малий `max_ticks_per_run=10` коректно обрізає прогін і
    позначає `truncated=True`.
- Живий запуск повного застосунку: `POST /api/backtest/run` через
  реальний HTTP підтвердив ті самі результати (подія з диском/threshold
  у відповіді, disclaimer присутній); graceful shutdown відпрацював штатно.
